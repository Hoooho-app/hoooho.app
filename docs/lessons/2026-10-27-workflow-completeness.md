## 设计缺口与长期纠正

| 容易遗漏的关系 | 实现前必须明确 |
| --- | --- |
| 消息与事项 | 连续补充是否属于同一事项；何时切换及怎样返回 |
| 原话与事实 | 地点/插话不等于症状；保留原话不等于结构化成功 |
| 回复与业务状态 | 接收、理解、草稿更新、正式保存有不同完成条件 |
| 异步与版本 | 新输入到来、旧结果迟到、手动更正、重试怎样合并或失效 |
| 保存与下游 | 真正保存的对象、版本和回执怎样体现在详情、入口、导出 |
| 失败与继续 | 内容保留在哪里，用户从哪继续，哪些副作用不得重复 |
| 规则与证据 | 先明确业务预期；模拟、真实服务、浏览器、线上证据分开 |

把以上关系迁移到其他业务时重新定义对象。不要将健康字段机械搬进日历、银行卡、保险或亲子内容。

## 将新方法应用到本次前台案例

任务：家长为当前选择的孩子分段描述同一次情况，获得可靠的追问和可核对草稿，保存后能打开对应记录，并供后续整理与交接。

以下是设计约束与后续核验依据，不是本轮运行验收通过记录。

| 阶段 | 业务规则与下一步 | 当前责任位置/需取得的证据 |
| --- | --- | --- |
| 选择孩子并开始 | 当前对象是归属依据；明确其他人时不得串写 | `server/ai/front-desk-record.mjs`、`front-desk-understanding.mjs`；需对象切换运行证据 |
| 输入“余杭” | 地点保留为上下文，不能无条件变为症状；含义不明时不擅自解释 | 理解与事实来源处理；需真实语义结果，不能仅凭护士回复 |
| 输入“头疼”“手脚冷” | 同一次情况的连续补充应完整进入当前事项；前一条未完成不丢后一条 | 前台服务、识别任务与客户端恢复；需顺序、归属、消息及事实版本证据 |
| 回应及追问 | 区分输入接收与理解结果，基于已知内容给出必要的一问，不以占位回复充当完成 | `front-desk-record.mjs` 与 `src/features/ai-business/SmartRecordWorkspace.tsx`；需真实模型多轮表现 |
| 查看及更正草稿 | 展示当前有效内容与不确定性；用户更正优先，旧解析不得覆盖 | `front-desk-continuous.mjs`、`front-desk-understanding.mjs`；需草稿、来源和版本一致证据 |
| 保存、重试及后台补全 | 按明确保存意图产生真实回执；原话保存与结构化区分；同 ID 补全，不重复建记录 | `front-desk-continuous.mjs` 的 `continuousCard`/`writeRecord`；需精确 ID 保存及回读证据 |
| 返回、刷新、打开及交接 | 恢复正确对象与事项；入口按结果出现；下游对应正确版本 | 前台客户端与清单逻辑；需实际浏览器及下游结果对照 |
