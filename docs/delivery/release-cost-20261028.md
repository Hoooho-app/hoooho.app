## 普通案例与恢复

负责人要求“提交这次记录页修改”：只启动必要的本地验证，提交代码并沿既有主分支规则发布共享网页，在线核对后关闭预览。没有原生变更就不重新上传 iOS 包；没有小程序发布要求就不上传小程序。负责人后来要求“提交 App Store 正式版”，执行者核对已测构建是否符合正式提交要求，选择该构建、补齐上架资料并提交审核，最终检查正式商店状态。

| 分支 | 保留与恢复 | 不能重复的副作用 |
| --- | --- | --- |
| 同一 PR 连续提交 | 最新版本验证接替旧版本；不同 PR、不同工作流互不取消 | 不让旧版本检查继续占用运行器 |
| 检查失败或发布失败 | 保留代码、失败证据及当前可用正式部署；从失败步骤修复 | 不把失败当作成功，不自动连发所有渠道 |
| 上传已成功、分组或审核未完成 | 先查 App Store Connect 中的构建状态，再继续分组或审核 | 不仅因等待 Apple 处理就重新上传同一版本 |
| 网页与已安装 App 共用后台 | 发布前检查对旧容器的兼容性；线上核对同一个服务 | 不把不同安装渠道当作数据隔离环境 |
| 需要真实模型或正式数据验收 | 沿用已授权预算、账号及写入边界；没有预算时保留本地合成验证结果 | 不从普通 PR 自动启动正式站模型调用或创建正式测试记录 |
