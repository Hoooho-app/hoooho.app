# 完整用户流程：设计与交付契约

生效日期：2026-10-27。适用：规划、设计、实现、缺陷修复、测试、审查及 ChatGPT/Codex 交接。

## 工作顺序

用户任务 → 完整案例 → 业务规则与状态 → 实现责任 → 验证证据 → 交付。

完整性由执行者主动承担。测试用于检验已明确的规则、发现遗漏，不能代替设计。用户只需决定真正的产品取舍，无须反复提醒“不能丢内容”“失败不能显示成功”等基础要求。

按任务大小裁剪以下模板：小改动简写；跨消息、跨页面、跨后台任务和持久化改动保留完整记录。纯文档变更检查范围、引用、冲突和版本，不增加无关运行测试。

## 一、任务与边界

- 谁，在什么场景下，为什么开始，最终要得到并使用什么结果？
- 当前代码/文档版本、用户最新确认的决定是什么？哪些仅是假设？
- 本次改什么，必要的直接依赖是什么，哪些页面、业务与数据保持冻结？
- 哪些常规选择由执行者解决，哪些尚未决定的取舍确实需要用户判断？

## 二、具体普通案例

用具体输入，从进入写到保存、重开、修改或交接。保留多次输入的顺序，不用“处理成功”跳过业务判断。

## 三、实现前必须回答的业务问题

- **归属：**谁的哪件事；补充、纠正、插话和新任务怎样区分；何时切换，歧义如何处理。
- **事实：**原件、原话、解析结果、草稿与正式记录的边界；每个字段的来源、默认值和不确定性；哪个对象是权威依据。
- **状态：**接收、理解、生成/更新草稿、保存分别如何完成；谁可推进状态，依据什么回执；哪些入口或下游动作由哪个状态触发。
- **顺序：**上一操作未完成时的新输入、并发处理、迟到结果和重复请求如何处理；旧结果不能覆盖什么；如何检查版本。
- **恢复：**取消、返回、刷新、退出、部分成功、超时、失败和重试后，从哪里继续，保留什么，不重复什么。
- **一致性：**对话、卡片、详情、列表、导出和直接关联模块如何使用同一份数据与版本。

对每个适用分支回答“用户接下来怎么办、已有内容在哪里、何时才算完成”。设计空白会影响正确性时，先补规则，再实现。不能用“收到”、空按钮或原话兜底掩盖理解/状态缺口。

允许沿用已确认的“原话先保存、之后同 ID 结构化”等能力，但不能把原话保存标成 AI 理解成功，不能借本规范擅自改变已确认产品交互。

按业务契约定义验收，不从现有行为倒推预期。程序测试、模拟供应商、真实供应商、真实持久化、浏览器与 Production 验证分别记录；大量模拟通过不证明 AI 语义能力。遵守当前调用预算与发布授权。

## 五、交付判断

分别记录设计、实现、验证、发布和用户验收状态。保存当前版本、实际证据、未验证项及影响；核心规则未闭合时不交付为完整可用版本。继承现有 Production 单环境政策，不创建新的环境或审批流程。

修复基础遗漏时，回到缺失规则，补全受影响链路，再检查相邻状态，并保留反例。参考 [前台教训与本次应用](../lessons/2026-10-27-workflow-completeness.md)。
