# Hoooho 过敏资料双向联动

用户要求：在任意过敏相关入口保存后，其他适用入口读取同一孩子的最新资料。原忌口卡「只改卡片，不写回档案」规则由本次要求替换。

## 实现行为

| 操作 | 联动结果 |
| --- | --- |
| 过敏史新增明确食物 | 卡片读取/展示新增食物；已有保存卡片同步更新 |
| 忌口卡新增「明确不能吃」食物并保存 | 在现有过敏档案中新增或关联明确食物，卡片保存稳定来源 ID |
| 忌口卡新增「暂时请避开」并保存 | 写入待排查档案，保留暂避安排；不混入新版明确过敏列表 |
| 卡片修改已关联食物名称或分组 | 修改同一档案条目，保留原 ID、报告、反应、来源及旧字段 |
| 档案修改、删除、恢复 | 同步卡片来源；删除后配料核对不再读取该记录 |
| 卡片取消选择、从本次清单移除 | 仅隐藏展示，不删除过敏资料 |
| 保存失败或版本冲突 | 不部分提交；保留正在编辑的草稿，显示冲突或重试反馈 |
| 两个浏览器页面同时使用 | 同源页面通过失效通知重读；重新获得前台焦点时重读 |

食物、药物、动物、环境、接触物沿用现有过敏分类。非食物过敏不进入餐厅用的食物清单。单纯提到吃过某种食物、候选关联、报告阳性不自动确认为过敏。家族成员的过敏不成为孩子本人的过敏。

## 数据路径

新增 `ProfileSectionStore`，作为既有 `health-profile-sections.json` 的写适配器，复用已有存储锁和事务；不增加第二套过敏数据库。一次写入中同时处理主档案及卡片投影，对实际变化的关联节增加版本。

接入三个写路径：登录后的档案保存、孩子档案简表命令、AI/资料核对后的现有归档。随记明确关联等既有客户端保存也走登录档案接口。食物扫描的个人冲突来源及就诊情况单仍读取原过敏节，因此新保存的卡片条目也能进入这些消费者。

客户端进入卡片即合并最新来源，保存响应带回当前孩子关联节以更新共享缓存。编辑草稿绑定开始编辑时的卡片版本和过敏档案版本，不能借用后来刷新的缓存版本覆盖新资料。账号清理和旧读取返回不会重新填入失效缓存。

## 兼容及限制

- 已有手工卡片项在下一次「保存并更新」时建立过敏来源关联；没有对生产历史资料执行批量回填。正式发布前需核对历史手工项数量及其明确/暂避分组，不能报告历史库已经完成回填。
- 旧待排查条目、报告、反应和其他历史字段保留；不因页面简化转换成明确过敏。
- 直接编辑存储文件或绕过这三个业务写路径的外部程序不属于本次联动入口。
- 已下载图片、HTML和已保存的历史医学原文是静态资料。本次更新的是当前来源；已有情况单继续使用现有过期/来源变化检查，新生成时读取新数据。
- 浏览器验证使用真实本地服务与登录/成员/档案接口、390×844移动视口，未模拟这些业务接口。未进行实体 iPhone Safari、Railway或生产用户数据验收。
- 保存发生版本冲突时草稿留在编辑页，用户需要重新核对最新资料；未做跨设备实时推送。
