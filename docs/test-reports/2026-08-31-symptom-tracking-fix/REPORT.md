# Hoooho 快捷记录事实链路修复回归报告

## 1. 结论

原报告基线为 35/100，65 个正式用例中 18 PASS、47 FAIL。本次修复后，原 65 用例全部通过；跨人物、否定反转、假设/问句阳性误入库和多事实静默丢失均为 0，预览—确认—刷新一致率为 100%。

## 2. 根因

- 解析只依赖笼统的 `family_member` 主体，未绑定健康事件真实 `memberId`，导致同段话中的记录者事实可能写入孩子事件。
- 前端把完整事实压缩成 `content` 后逐条创建记录，服务端再次解析简化文本，造成时间、人物、侧别、程度、次数和持续时长丢失。
- 规范化阶段丢弃否定事实，且状态只依赖单次输入内的最近目标，无法形成跨记录病程链。
- 条件、问句、担忧、引用等语用门禁不完整，医疗词命中可被误当成已发生事实。
- 时间解析未始终采用最长表达，日期精度和未来时间拒绝没有贯穿预览与确认。

## 3. 修复验证范围

- 服务端权威主体解析与多人物 fail-closed 门禁。
- 服务端 `previewId` 草稿、校验和、过期和归属检查，以及幂等原子确认。
- 原始输入单记录保存与完整结构化事实快照持久化。
- 事实人物、极性、状态、部位、侧别、程度、次数、频率、持续时长和时间语义。
- 事件级 active/persistent/improving/worsened/resolved/recurrent/corrected 状态上下文。
- 条件、问句、担忧、引用、转述、指令和闲聊的 clause 级安全门禁。
- 快捷记录预览中的真实人物名和结构化字段；离线、未来时间、多人物和模糊指代中文错误。
- 旧记录读取兼容与现有紧凑时间轴保持不变。

## 6. Staging 在线回归

- 环境：Railway `staging` / `hoooho.app`。
- URL：`https://hooohoapp-staging.up.railway.app`。
- `/`：HTTP 200。
- `/api/health`：HTTP 200。
- 多人物输入：返回 `MULTIPLE_SUBJECTS_NEED_SPLIT`，未生成 preview。
- 假设问句：`hasHealthFacts=false`，0 条阳性事实，无可确认 `previewId`。
- 结构化输入：一次预览得到 3 条事实，人物为隔离测试宝宝，保留右侧小腿、严重、两小时、呕吐三次和体温。
- Confirm：一次保存 1 条原始来源记录和 3 条事实；重试返回幂等结果，无重复记录。
- Refresh：记录和 Organization 事实与确认响应逐字段一致。
- 否定输入：保留阴性历史，阳性事实为 0。

在线测试仅使用新建的隔离虚构账号和事件，没有读取、修改或删除真实用户健康数据，也未清理此前保留的 Staging 测试数据。
